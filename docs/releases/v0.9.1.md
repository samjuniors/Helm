# Helm v0.9.1 — Windows PATH Onboarding Fix

**Type:** PATCH — fixes the Windows command-not-found experience introduced by managed installations.
**Compatibility:** Node.js 18+, Git, 14 MCP tools unchanged.

## What's fixed

A successful v0.9.0 installation created `%USERPROFILE%\.helm\bin\helm.cmd` but did not add that location to the Windows user PATH. This meant opening PowerShell and typing `helm update` could fail with “helm is not recognized”.

In v0.9.1, the Windows managed installer now:
- Adds the launcher location to the **current user's PATH**, without replacing other entries or touching the system PATH. The change is idempotent and retains existing variable references and registry value type.
- Shows a clear notice when another terminal must be opened. The version-pinned PowerShell bootstrap also adds the launcher to the current PowerShell session.
- Allows `--no-path` to opt out. On non-Windows systems, shell profile settings are left untouched and manual PATH instructions remain available.
- Cleans up Helm's PATH entry during uninstall only when Helm recorded that it added it. Manually configured PATH entries are preserved.
- Repairs older managed installations when users run `helm install` again; existing plugin files and project data are not overwritten.

## Upgrade

For an existing v0.9.0 managed installation whose command is not recognized, use its full launcher path to update:

```powershell
& "$HOME\.helm\bin\helm.cmd" update
& "$HOME\.helm\bin\helm.cmd" install
```

Then reopen PowerShell and run `helm version`. If the first command cannot be found, use the verified bootstrap or manual upgrade guide.

For new users, follow the reviewed, tagged PowerShell bootstrap link in the [installation guide](https://github.com/samjuniors/Helm/blob/main/docs/INSTALLATION.md). You may opt out of automatic user PATH modification with `-NoPath` in bootstrap or `--no-path` in setup.

## Safety and test coverage

The patch modifies only the user-scoped PATH, never the system-wide PATH. Existing projects, Git history, custom files, and MCP server registrations are preserved. Tests use a disposable registry test key rather than changing a tester's real PATH. Hosted Windows/Ubuntu tests, any remaining host-specific limitations and release-archive acceptance are recorded on the release PR.
